# Dev-Flow 轻量开发与理解

让用户能依据真实代码说明“改了什么、为什么、怎样验证”。默认自动推进已授权任务，不要求逐步确认或答题；用户明确要求暂停、先讨论方案或禁止写文档时遵从用户要求。

技能是否被选用取决于客户端和任务描述。随插件提供的 `PostToolUse` hook 在成功运行时注入提醒，不保证模型实际遵循，也不覆盖未匹配的编辑工具。

## 开工：按需定位与任务地图

1. 读取适用的项目规则，查看工作区已有改动与相关 diff，记住本次改动前的状态；没有 Git 时直接核对相关文件。不要把已有改动算作本次产出。
2. 优先用已有项目索引定位入口、直接依赖和相关测试。若已有相关经验索引，或任务涉及反复返工、重要约束、关键设计，按需读取 [维护指南的项目记忆部分](references/maintenance.md#项目记忆)，先检索相关条目，再核对当前代码。信息不足时才扩大读取范围，不通读整个项目和历史记录。
3. 实质开发任务在首次修改前用约 5～8 行说明：目标、关键调用链、改动边界、验收方式。修 bug 区分“已确认根因”和“待验证假设”；新功能说明如何衔接现有流程。若已有计划，补充缺失信息即可。

目标与授权明确时继续执行。分析、验证深度与任务影响相称，不自动切换模型或修改推理配置。

## 编码：短流水线

长任务中每完成一个方法、一个文件、一个逻辑块或一个关键决策，立刻播报，再继续下一处代码。同一次改动同时满足多个条件时只播报一次；长任务中的单行文件改动也需要播报。

```
=== 流水线 [当前步骤/总步骤] ===
文件：<相对路径>
做了什么：<业务行为发生了什么变化>
决策点：<有代码或需求依据的选择原因>
下一步：<接下来要改什么>
```

保持五行短提示，步骤编号对应现有计划；计划变化时更新编号，不凭空宣称已完成。关键逻辑可在“文件”中附函数或行号。机械改动如实说明，不虚构备选方案，也不逐行复述代码。

例如，确认重复回调的并发问题后：

```text
=== 流水线 [2/4] ===
文件：src/order/callback.ts，handleCallback
做了什么：相同业务键的重复回调现在返回已处理结果。
决策点：先查再插无法保证并发唯一性，使用已有唯一约束识别重复请求。
下一步：验证并发回调只产生一条业务记录。
```

同一问题连续两次修复仍未通过对应验证，或根因假设被证据否定时，先停止追加猜测性补丁，读取 [失败重诊断](references/maintenance.md#失败重诊断)。不把普通编译错误修正机械地计作根因反复失败。

## 完工：验证、走读与理解

先执行与改动相称、环境允许的检查，再输出一份合并总览；检查无法执行时如实说明。总览按任务复杂度压缩，包含：

- **完整链路**：一行串起入口、核心处理、数据变化及返回结果，也串起本次流水线节点。
- **值得看的代码**：最多三个文件位置及函数或行号，指出需要理解的判断或约束；不引用虚构行号。
- **验证证据**：实际执行的命令或手工操作、结果与未验证项。区分通过、失败、未运行和仅建议执行；不能把 AI 建议的测试算作已运行，或把测试通过说成绝对无风险。
- **QA 说明**：用简短一段串起“现象／需求 → 根因／方案 → 改动 → 验证 → 剩余风险”。已在总览说明的事实直接复用，不重复生成另一套报告。

有实质业务逻辑时，结尾给一道基于本次代码的可选行为预测题，例如“数据库写入成功但消息发送失败时，当前实现会留下什么状态？”不同时给答案、不泛泛问“理解了吗”。用户回答后结合代码反馈；跳过或提出新任务时正常继续，不把答题作为交付门槛。

结束时判断是否值得沉淀：普通任务优先补充已有记录；重要业务约束、隐蔽 bug、反复返工、关键设计或跨会话任务，按需读取 [项目记忆](references/maintenance.md#项目记忆) 并记录事实。没有复用或交接价值时不新增文档。

## 按需交接与复盘

- 用户准备换窗、暂停或明确需要接续时，读取 [交接](references/maintenance.md#交接)，按已授权的记录约定保存状态；禁止写文件时仅在回复中给摘要。不要自动结束仍可推进的任务。
- 用户明确要求开发复盘时，读取 [复盘](references/maintenance.md#复盘)，先提出有证据的改进候选。未经明确要求，不把经验写成全局规则或修改技能。
- 纯问答、纯解释和一眼能核对的微小改动不执行完整流程、不自动新增记忆、不出理解题。显式交接或复盘按对应部分执行，不制造编码流水线。

## 辅助工具与边界

需要补充查看仓库当前改动时，在目标项目中运行本技能目录下的脚本。先根据当前客户端找到包含本 `SKILL.md` 的目录，再使用该目录下的 `scripts/gather.sh`；不要在插件仓库中收集另一个项目的 diff。

```bash
bash "<本技能目录>/scripts/gather.sh" all
bash "$HOME/.agents/skills/dev-flow/scripts/gather.sh" all  # Codex 直接安装
bash "$HOME/.agents/skills/dev-flow/skills/dev-flow/scripts/gather.sh" all  # Codex 插件式仓库
bash "$HOME/.claude/skills/dev-flow/skills/dev-flow/scripts/gather.sh" all  # Claude Code 本地插件仓库
```

Claude Code 可用 `claude plugin details dev-flow` 和 `claude plugin list` 确认安装位置；Codex 的路径来自实际技能目录。示例路径需要按客户端的安装方式选择其中一条，不把它们同时当作有效路径。

- `auto`：默认，有暂存改动就只展示暂存 patch，否则展示未暂存 patch；混合状态会遗漏另一部分正文。
- `staged`：只展示暂存 patch。`all`：有 HEAD 时展示相对 HEAD 的已跟踪文件最终差异，暂存和未暂存相互抵消的变化需分别查看；没有 HEAD 时回退到脚本的暂存优先逻辑。
- 未跟踪文件仅列名，需要单独查看本任务相关文件。`MAX_DIFF_LINES` 默认 2000，截断后按文件补查。
- 输出是仓库快照，不是会话归属证明或测试证据。结合初始状态与实际编辑记录归纳；无法区分归属时明确说明。脚本命令报错或没有输出不等于没有改动。

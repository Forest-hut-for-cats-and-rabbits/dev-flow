# Dev-Flow 轻量开发与理解

让用户能依据真实代码说明“业务怎样流转、为什么这样实现、怎样验证”。默认自动推进已授权任务，直接提供核心问题的答案，不要求逐步确认或答题；用户明确要求暂停、先讨论方案或禁止写文档时遵从用户要求。

技能是否被选用取决于客户端和任务描述。

## 开工：按需定位与任务地图

1. 读取适用的项目规则，查看工作区已有改动与相关 diff，记住本次改动前的状态；没有 Git 时直接核对相关文件。不要把已有改动算作本次产出。
2. 优先用已有项目索引定位入口、直接依赖和相关测试。若已有相关经验索引，或任务涉及反复返工、重要约束、关键设计，按需读取 [维护指南的项目记忆部分](references/maintenance.md#项目记忆)，先检索相关条目，再核对当前代码。信息不足时才扩大读取范围，不通读整个项目和历史记录。
3. 实质开发任务在首次修改前用约 5～8 行说明：目标、关键调用链、改动边界、验收方式。修 bug 区分“已确认根因”和“待验证假设”；新功能说明如何衔接现有流程。若已有计划，补充缺失信息即可。

目标与授权明确时继续执行。分析、验证深度与任务影响相称，不自动切换模型或修改推理配置。

## 大需求计划后：产品与测试双评审

当计划已形成并满足 [计划评审指南](references/plan-review.md) 中的大需求判据时，在实施前直接启动两个独立子代理评审同一版计划。仅要求先 Plan 或处于 Plan 模式不单独构成触发条件；该计划同时符合判据时照常评审。未命中判据的小型计划、普通方案讨论、纯进度更新和无行为变化的机械修改不自动触发；用户明确要求“评审这个计划”时无条件执行。

先读取 [计划评审指南](references/plan-review.md)。向两个子代理提供相同的原始需求、计划版本、业务与代码事实、已知约束和验收目标，先不共享彼此的结论。产品代理检查目标、范围、业务流程、业务规则和用户价值；测试代理检查验收可测性、正常与异常路径、回归范围和测试环境。两者只做评审，不修改业务代码。

主代理汇总问题，按“阻碍实施／需澄清／建议”区分，附计划位置、依据、影响和修改建议；采纳后修订计划，不擅自扩大用户范围。关键产品取舍无法从需求或代码确认时询问用户。计划的目标、范围、流程、验收或实现策略发生实质变化时，让两个角色复核新版；措辞或进度更新不重复评审。

处于仅规划或 Plan 模式时，评审后交付修订计划并停在该阶段，不开始编码或自行切换模式；已有实施授权且没有未解决阻碍时继续开发。角色失败可重试一次；恢复后补跑缺失角色，仍然失败时按“双角色完成／仅产品完成／仅测试完成／双角色未完成”保留最终状态。若缺失视角关系关键范围、验收或回归且主代理不能核实，标为未解决阻碍并暂停相关实施；其余情况说明缺口和已有授权后再推进。不得由一个代理同时充当两个角色。

## 每个业务实现后：结合代码汇总节点

以可独立验收的业务行为为单位，例如提交订单、处理支付回调或查询审批结果。一个业务涉及多个文件或方法时，合并走读；不按每次编辑播报，也不使用固定五行模板或步骤计数。

实现该业务的相关代码后，继续下一项业务前给出简短摘要；只有一项业务时可与完工总览合并。先用一行串起实际业务链路，再按需用表格说明节点：

| 业务节点 | 代码位置 | 关键处理与判断 | 结果或状态变化 |
| --- | --- | --- | --- |
| 按当前实现填写 | 文件路径与函数，必要时附核实过的行号 | 该节点接收什么、受什么条件约束 | 返回值、持久化结果或下一节点 |

覆盖实际存在的入口、校验、核心处理、数据或状态变化、外部调用和返回结果；关键异常、重试、重复请求等分支存在时一并说明。不为凑节点虚构模块或引用不存在的代码。尚未测试时标明“实现完成，待独立测试”，后续修复改变了节点行为时同步更新摘要。

## 失败时重新诊断

同一问题连续两次修复仍未通过对应验证，或根因假设被证据否定时，先停止追加猜测性补丁，读取 [失败重诊断](references/maintenance.md#失败重诊断)。不把普通编译错误修正机械地计作根因反复失败。

## 编码结束后：直接交给子代理独立测试

完成编码和必要的本地检查后，在最终交付前直接调用当前客户端可用的子代理能力，不另等用户确认。启动前读取 [独立测试指南](references/independent-testing.md)，交付原始需求与验收条件、准确的项目路径、最终代码及本次改动范围，并提供该指南及 [测试设计指南](references/test-design.md) 的可访问位置或必要正文。

测试子代理从需求出发建立场景覆盖表，沿实际调用链确定范围；按业务风险选择条件组合、状态转换、边界、故障、部分失败、并发及兼容验证，复用项目已有工具。用户报告的原始问题、适用的关键异常和受影响回归列为必测，实际检查返回结果、数据状态及不应发生的副作用；客户端、接口和数据库分别保留证据，不能互相冒充覆盖。简单任务只选适用场景。

子代理测试时，主代理可整理业务链路和核心问答，但不修改正在验证的业务代码。拿到结果后核对实际命令、结果与所测代码；发现问题就在原授权范围内修复，再让子代理复测相关场景。最终结论必须对应最后一次相关代码修改之后的验证。重复失败按失败重诊断处理。

当前客户端没有子代理能力、调用失败或环境阻止执行时，如实说明原因，执行主代理可完成的检查并标明“未完成独立测试”。不得把主代理自测、静态走读或未执行的测试计划称为子代理测试通过。

## 完工：业务清单、技术方案、易错点与问答

待独立测试返回并处理其发现后，给出一份合并总览，复用此前的节点摘要，不再重复逐文件报告。按需求复杂度压缩，但让用户能回答“完成了哪些业务、流程如何工作、使用什么关键技术、哪里容易出错及如何防护、怎样验证”。包含：

- **功能完成清单**：逐项列出实现的用户可见业务能力、对应状态（完成／部分完成／未完成）及相关代码位置；未实现或被明确排除的内容不写成已完成。
- **业务流程与代码**：逐项说明入口、关键判断、数据或状态变化、外部调用和返回结果，引用真实文件与函数；详细节点已说明时只补充最终变化。
- **核心技术方案**：解释支撑关键流程的实际方案及采用原因，例如事务边界、幂等策略、状态机、缓存、消息投递或权限校验。只写代码中实际采用且与本需求相关的技术，链接到对应实现；简单任务可以精简为一两项。
- **易错点与防护**：列出本次容易出错的边界或失败场景、可能后果、实际使用的防护技术和代码位置，例如唯一约束防重复、事务保证一致性、重试与退避、输入校验、超时／熔断或补偿。区分“已实现防护”“发现但未处理”“仅建议”，不把建议说成现状。
- **验证证据**：区分主代理自检与子代理独立测试，关联场景、预期依据、验证层次、实际命令或手工操作及结果。保留原始问题、关键异常、相关回归和未验证项；必测项失败或未执行时明确“失败”或“验证不完整”，不以用例数量、高覆盖率或其他测试通过概括整体通过。不能把计划当作已运行。
- **核心问题与答案**：挑选本需求最值得理解的业务规则、根因、设计选择、状态一致性或异常边界问题，逐个直接给出答案。每个答案关联代码依据，涉及运行结果时关联测试证据；未验证的推断明确标注，不猜测答案。不使用只有题目、不给答案或等待用户作答的形式。
- **交付状态与限制**：简短说明需求实现了什么、修复了什么、尚有哪些未完成或未验证事项。独立测试受阻时明确保留该状态。

总结只覆盖本次需求范围内实际存在的业务与技术。小改动可合并或省略不适用部分，但不得为填表臆造技术方案、错误场景或防护；发现的风险尚无防护时直接标明。问题数量随业务复杂度控制，不强凑题数或泛泛提问。用户另行明确要求测验或暂不看答案时，再按用户要求处理。

结束时判断是否值得沉淀：普通任务优先补充已有记录；重要业务约束、隐蔽 bug、反复返工、关键设计或跨会话任务，按需读取 [项目记忆](references/maintenance.md#项目记忆) 并记录事实。没有复用或交接价值时不新增文档。

## 按需交接与复盘

- 用户准备换窗、暂停或明确需要接续时，读取 [交接](references/maintenance.md#交接)，按已授权的记录约定保存状态；禁止写文件时仅在回复中给摘要。不要自动结束仍可推进的任务。
- 用户明确要求开发复盘时，读取 [复盘](references/maintenance.md#复盘)，先提出有证据的改进候选。未经明确要求，不把经验写成全局规则或修改技能。
- 纯问答、纯解释和仅调整说明文档的任务不启动代码测试子代理、不强加业务节点或核心问答。微小代码改动压缩走读与汇总，但仍由子代理执行与改动相称的检查，不为凑测试新增无价值的测试用例。上述任务不自动新增记忆；显式交接或复盘按对应部分执行。

## 辅助工具与边界

需要补充查看仓库当前改动时，在目标项目中运行本技能目录下的脚本。先根据当前客户端找到包含本 `SKILL.md` 的目录，再使用该目录下的 `scripts/gather.sh`；不要在插件仓库中收集另一个项目的 diff。

```bash
bash "<本技能目录>/scripts/gather.sh" all
bash "$HOME/.agents/skills/dev-flow/scripts/gather.sh" all  # Codex 直接安装
bash "$HOME/.agents/skills/dev-flow/skills/dev-flow/scripts/gather.sh" all  # Codex 插件式仓库
bash "$HOME/.claude/skills/dev-flow/skills/dev-flow/scripts/gather.sh" all  # Claude Code 本地插件仓库
```

Claude Code 可用 `claude plugin details dev-flow` 和 `claude plugin list` 确认安装位置；Codex 的路径来自实际技能目录。示例路径需要按客户端的安装方式选择其中一条，不把它们同时当作有效路径。

- `auto`：默认，有暂存改动就只展示暂存 patch，否则展示未暂存 patch；混合状态会遗漏另一部分正文。
- `staged`：只展示暂存 patch。`all`：有 HEAD 时展示相对 HEAD 的已跟踪文件最终差异，暂存和未暂存相互抵消的变化需分别查看；没有 HEAD 时回退到脚本的暂存优先逻辑。
- 未跟踪文件仅列名，需要单独查看本任务相关文件。`MAX_DIFF_LINES` 默认 2000，截断后按文件补查。
- 输出是仓库快照，不是会话归属证明或测试证据。结合初始状态与实际编辑记录归纳；无法区分归属时明确说明。脚本命令报错或没有输出不等于没有改动。

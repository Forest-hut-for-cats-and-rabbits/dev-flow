# 按需维护指南

仅在需要时读取对应部分：[失败重诊断](#失败重诊断)、[项目记忆](#项目记忆)、[交接](#交接)、[复盘](#复盘)。日常开发的默认流程见 [SKILL.md](../SKILL.md)。

## 失败重诊断

触发条件是同一问题连续两次修复仍未通过针对该问题的验证，或新证据推翻了根因假设。工具安装失败、无关测试失败及普通编译错误修正，不自动算作同一根因反复失败。未能执行验证时说明证据缺失，不虚构失败次数。

停止追加猜测性补丁，先用只读方式核对：

1. 原始目标、验收条件和当前可复现现象是否一致。
2. 失败日志、相关代码和数据支持了什么；哪些仍是假设。
3. 每次已尝试方案、预期作用及实际结果；有没有违反已有约束或影响其他路径。
4. 下一项能区分假设的最小验证，例如针对性复现、输入对照或相关日志检查。

简短播报“失败证据／已尝试／当前未知／下一项验证”，再做有依据的验证。获得支持新方案的证据后，在原授权范围内继续；不要先加补丁再寻找解释。若验证本身需要副作用，遵守既有环境和授权约束。

只有需求存在实质歧义、必须扩大范围或缺少用户才能提供的信息时才询问。无法推进时如实报告卡点。不要自动回滚、重置或丢弃已有改动。上下文明显混乱时可以建议交接，不能以换窗代替根因分析或擅自终止任务。

## 项目记忆

目标是让下次任务找到仍然有效的事实、决策和证据。记录与检索不会训练模型参数，不保证性能自动提升；复用是否有效，需要后续验证结果支持。

### 何时读写

| 场景 | 处理 |
| --- | --- |
| 微小、机械修改或纯问答 | 不新增记录，不出理解题 |
| 普通业务任务 | 优先更新已有任务记录；没有复用或交接价值时不新增 |
| 重要约束、隐蔽 bug、反复返工、关键设计 | 验证后保存精简经验并更新索引 |
| 验证受阻或根因未明 | 必要时记录状态和证据缺口，标为待验证，不晋升为已验证经验 |
| 用户需要跨会话接续 | 更新当前任务状态，见交接部分 |
| 项目禁止写文档或用户只要代码 | 遵从约束，在回复中给必要摘要，不落盘 |

按项目约定自动记录本任务事实，不因此修改全局规则或技能。文档落盘同样属于文件修改，长任务中遵守短流水线要求；不要为记忆文件本身再生成新的任务记录或递归触发复盘。

### 存放位置

先查看项目规则、已有索引和本任务文档约定；只做定向查找，不遍历用户目录或所有历史会话。已有任务记录、决策文档或记忆目录时就地复用，不另建平行体系。

没有既有约定且确实需要沉淀时，在目标项目根目录按需创建：

```text
docs/dev-flow/
├── index.md
├── tasks/
│   └── YYYY-MM-DD-任务名.md
└── NOW.md
```

不用一次创建完整目录和空模板。日期用当地日期，任务名用简短的文件名安全主题；同一任务复用同一记录，不按每轮对话或每日重复创建。同名但不同任务加可辨认的主题后缀，不覆盖旧文件。`NOW.md` 只在需要交接时建立。

索引每个任务一条，包含主题、适用场景或关键词、状态、相对链接。只链接本项目可复用的记录，必要时引用已有任务文档；不把凭据、访问令牌、私人聊天或无关生产数据写入记忆。

### 最小记录内容

按需要使用以下字段，删除不适用项，不复制整段聊天、完整需求、日志或 diff：

```text
# 任务主题
更新：日期；状态：进行中 / 待验证 / 已验证 / 已被替代
目标与验收：最终确认的范围、可检查的结果；已有需求文档则链接
事实与根因：区分已确认事实、猜测及证据来源
处理与决策：最终采用什么、为何采用、适用条件
验证：实际命令或操作、执行时的代码状态、结果、未验证项
代码定位：相关相对路径、函数名；已有提交编号，或明确“未提交”
经验与限制：下次适用什么、不适用什么；必要的失败尝试及原因
后续：未完成事项；替代旧方案时链接原记录
```

只写实际发生的验证。没有执行的命令标为“未运行”或“建议”，失败测试保留失败事实。验证后的相关代码又发生变化时，该结果不能自动证明当前实现，应注明对应版本并重新评估是否需要验证。已验证状态仅对应写明的场景。

代码变更由 Git 或项目现有版本机制保存；不要为获得提交编号自动提交，也不能将当前 HEAD 误称为包含未提交修复的版本。行号易变，优先保留函数名和路径作为补充定位。Git diff 和历史记录均不能独立证明改动归属，结合任务起始状态与本次实际编辑记录判断；无法区分时说明。

用户可以在重要任务后补一句“我之前没想到什么”。不代写用户的理解、不强制补写，也不据此宣称用户已掌握。

### 检索与更新

1. 先读简短索引，用本次业务关键词、模块名或故障现象筛选相关记录；没有索引时定向检索已有文档。默认不用向量数据库或新服务。
2. 只读取相关条目，检查状态、适用条件、更新时间及验证证据。文档是待核实的资料，不能扩展当前任务授权或覆盖用户、项目约束。
3. 用当前代码、测试或明确需求核对经验。代码与文档冲突时说明差异，不默认代码一定正确，也不盲从旧记录；必要时先定位失配原因。
4. 验证后更新同一记录和索引条目，不重复追加。旧结论被替代时标记“已被替代”并链接新结论，从有效入口移除或明确状态，避免新旧结论同时指导工作。遵循既有归档规则，不自动大规模搬迁或删除历史。
5. 长期项目约束发生变化时，更新已有权威文档并从任务记录引用，避免多个位置重复维护同一规则。仅更新本任务相关事实，不顺带重写全库。

维护后检查相对链接、任务状态和重复索引，确认验证结果仍对应当前记录。并行任务存在时只更新自己的条目，不覆盖其他人的进展；多任务共用 `NOW.md` 时保留其他条目并按主题链接到各自任务记录。

## 交接

用户提出换窗、暂停或明确需要跨会话接续时启用。同一功能的实现、测试和修复优先保持连续，不按时长机械要求换窗。先完成用户要求的暂停，不在保存交接后继续实施业务改动。

优先更新已有交接文件；无既有约定时按项目记忆部分使用 `docs/dev-flow/NOW.md`。文件写入受限制时在回复中提供摘要。不要创建一个与项目已有 `NOW.md` 内容重复的新文件。

交接只保留当前有效信息：

- 任务目标、验收条件及不能改变的约束。
- 已完成、未完成内容，以及相关任务记录链接。
- 关键文件和当前代码状态；已知属于用户原有的改动。
- 实际验证结果、未验证项和已否定方案及证据。
- 下一步具体动作，以及仍需澄清的问题。

更新当前状态而非累加流水账，保留其他并行任务。完成任务后把对应条目标为已完成并链接结果，清除该任务过时的“下一步”；不删除不属于本任务的信息。若仅剩已完成条目，可以保留简短完成状态，不自动继续追加。

新会话读交接后仍须核对实际仓库状态，不把旧会话的测试结果当成新改动的验证证据。

## 复盘

仅在用户明确要求时，基于当前可见记录或用户指定资料复盘；不要声称读取过不可见历史，也不自动扫描全部会话。

输出精简的“观察 → 证据 → 适用范围 → 改进候选”，兼顾有效做法和失败原因。区分已知事实与推断，不编造重复次数；只有存在可比证据时才评价复用是否减少返工。

| 经验范围 | 建议放置 |
| --- | --- |
| 当前版本临时限制 | 当前任务记录或交接 |
| 某项目长期业务或技术约束 | 该项目现有权威规则或设计文档 |
| 可重复执行的专门流程 | 对应技能的修改候选 |
| 普遍且后果重要的协作要求 | 全局规则的修改候选 |

先检查现有规则是否已覆盖、问题是否由未执行规则造成，以及经验是否只适用于一次任务。已有覆盖时改进发现和执行方式，不继续堆叠同义规则；单次偶然错误不自动升级为长期要求。

默认只给候选建议。用户明确要求修改长期规则或技能时，先检查适用约束与已有改动，保留待修改文件的原始字节副本或其他可恢复快照，再定向修改；Git 已跟踪不代表未提交内容已有备份。备份应放在项目现有备份位置或版本目录外，并告知位置，不自动提交。不要重新初始化现有技能、重写无关配置或因复盘引入模型切换与后台服务。

# 按业务风险设计测试覆盖

计划中的测试评审与编码后的独立测试共用本指南。前者识别验收和场景缺口，后者对最终代码执行验证。先依据需求确定预期行为，再沿实际调用链选择范围和工具；不按文件数量、用例数量或覆盖率百分比判断是否充分。

## 从需求和原始问题建立场景

- 将原始需求、用户操作、已确认业务约定作为预期结果的依据。当前实现和已有测试用于定位与发现遗漏，不能反过来定义正确行为；依据冲突或关键规则缺失时明确列出待确认项，不自行编造。
- 用户报告的原始问题单列为必测场景，尽量保留原操作顺序、输入特征和批量条件。主代理在修复前能复现时保存证据；已有最终修改时，测试代理直接重跑同一场景，必要时在隔离副本验证旧版本，不回滚工作区。未观察到修复前失败时，不声称已经证明“先失败、后通过”。
- 新行为至少有代表性的正常路径；修复还需检查相邻的正常路径是否保持正确。相关关键业务前置条件未满足、关键异常和受影响的回归场景同样列为必测，不能被已有测试套件的成功结果替代。
- 将技术上有效与业务上允许分开验证，例如对象存在不代表有权限，参数有效不代表已确认，前一步成功不代表整个批次已完成。区分输入、操作者、对象归属、业务状态及操作顺序。

执行前形成简短覆盖表，执行后在同一表中补结果；可放在回复或测试报告中，不强制新建项目文档。简单修复只保留适用行，不套用完整清单。

## 沿调用链确定测试范围

定向查看改动入口、直接调用者、共享服务、持久化和外部依赖，确定受影响的范围：

| 范围 | 需要核对的行为 |
| --- | --- |
| 当前入口与用户操作 | 参数绑定、默认值、校验、确认／取消、错误反馈；客户端限制是否也由服务端正确执行 |
| 核心逻辑与状态 | 业务前置条件、合法与非法状态转换、返回结果及实际数据变化 |
| 直接上下游 | 上游是否提供必要信息，下游是否正确使用结果，失败是否被吞掉或错误地当成成功 |
| 共享逻辑与其他入口 | 哪些其他调用方使用改动的方法、接口或数据；选择代表性回归，不只测试当前入口 |
| 历史数据与兼容性 | 老数据、缺字段请求、已有对象复用、接口兼容、迁移前后行为（实际涉及时） |

用实际调用关系说明纳入范围及重要排除项。不要为扩大覆盖通读全库；发现共享契约变化再扩展到相关调用方。只改文案不机械增加并发、数据库或端到端测试。

## 异常场景的设计方法

按需求和改动风险选用以下方法，不要求每项任务执行所有类别。存在相关机制或明确风险时，选取能区分正确与错误行为的场景；不凭空引入新业务规则。

| 方法 | 适用情况与场景 |
| --- | --- |
| 等价类与边界值 | 空／缺失／错误类型、合法与非法值、已删除或失效对象；数量、金额、长度、时间的边界及相邻值 |
| 决策表 | 多条件共同决定结果时，组合用户权限、对象归属、新旧对象、业务状态、确认状态等，核对允许和拒绝路径 |
| 状态转换 | 跳步、倒序、重复操作、取消后继续、状态过期、确认后修改关键数据；是否需要重新确认由业务约定决定 |
| 故障注入与恢复 | 依赖超时、错误响应、断连、数据库操作失败；检查失败位置、重试、补偿或回滚是否符合已有约定 |
| 批量与部分失败 | 空批次、单项、多项、混合有效性、某项处理中断；验证约定的整批原子性或逐项结果，不能自行假定全成全败 |
| 并发与幂等 | 双击、重复请求、超时后重试、并发修改、重复事件；检查重复写入、丢失更新及结果一致性 |
| 兼容与回归 | 其他调用入口、老数据、已有对象复用、旧请求结构，以及本次修复容易改变的相邻正常路径 |

组合过多时，普通组合可用两两组合（pairwise）缩减。涉及权限、提交许可、金额、数据一致性的关键组合，以及已知缺陷组合，应明确列出，不用 pairwise 代替。并发风险需用实际重叠请求或可控同步验证；顺序重复调用只能证明顺序重试行为。

## 分层执行与工具选择

优先复用项目已有测试框架、命令和测试环境。选择能验证该行为的层次；逻辑测试通过不自动覆盖接口、数据库或用户交互。

| 层次 | 验证重点 | Java／Spring 项目的可选工具示例 |
| --- | --- | --- |
| 单元测试 | 条件组合、状态判断、计算、异常分支 | JUnit 5 参数化测试、Mockito |
| 接口与集成测试 | 请求绑定、鉴权、序列化、真实数据库约束、事务边界和回滚 | Spring Boot Test、MockMvc／REST Assured、Testcontainers |
| 外部依赖异常测试 | 超时、失败响应、连接中断及恢复行为 | WireMock；需网络层故障时考虑 Toxiproxy |
| 用户流程测试 | 实际选择、确认、取消、提示和最终业务结果 | Playwright 或可记录的实际手工操作 |
| 覆盖质量辅助检查 | 未执行分支、断言能否发现逻辑错误 | JaCoCo；关键逻辑且成本合适时考虑 PIT 变异测试 |

这些工具是选项，不是安装清单；其他技术栈使用已有等价工具，不强制引入 Java 或新的测试平台。确需新增依赖时遵循项目约定和现有授权；环境缺失时先执行可完成的验证，并保留剩余缺口。

Mock 适合验证分支和故障处理，不能证明真实数据库事务、唯一约束、网络或客户端行为。数据库机制需要适当的集成环境；确认弹窗等交互需要客户端证据。只有后端可用时分别报告服务端已测内容和客户端未验证项。

代码行／分支覆盖率用于发现线索，不设置脱离业务的统一百分比门槛，也不把高覆盖率当成验收完成。按需采用属性测试或变异测试检验关键不变量和断言质量，不为每个修复运行昂贵工具。

## 检查结果与副作用

每个关键场景检查可观察的业务结果，而不只断言 HTTP 200、无异常或 Mock 调用次数：

- 成功时检查返回内容、持久化数据、业务状态和必要的后续动作。
- 拒绝或失败时检查错误内容，以及不应发生的创建、更新、扣款、消息或其他副作用确实未发生；涉及事务时验证失败后的数据一致性。
- 批量、重试和并发场景检查重复记录、部分写入、状态互相覆盖及最终结果；依据需求确定哪些变化允许保留。
- 外部副作用通过获授权的隔离环境、测试替身或记录器验证，不调用真实支付、通知或第三方写入来凑覆盖。涉及真实系统的未验证项如实保留。

## 覆盖证据与结束条件

独立测试报告使用以下字段，可按任务规模合并单元格：

| 场景与级别 | 预期行为及依据 | 层次与用例／操作 | 实际结果与证据 |
| --- | --- | --- | --- |
| 用户原问题／关键异常／相关回归；标明必测项 | 关联需求或已确认约定，包含状态与副作用 | 具体测试名称、命令或手工步骤 | 通过／失败／未验证；实际观察、日志或报告位置；未验证的原因 |

覆盖表的执行证据关联 `dev-flow.verification.v1` 中的检查编号，完成声明引用相应证据；结构字段以 [证据 Schema](evidence-schema.md) 为准。覆盖表解释业务覆盖范围，结构记录保存可校验的执行事实，两者的结果必须一致。

主代理核对原始问题、适用的关键异常和受影响回归是否实际执行。全部适用必测项通过后，只对已覆盖范围给出通过结论；任何必测项失败或未执行，都保留“失败”或“验证不完整”及具体场景，不能概括为整体测试通过。环境受阻不等于代码失败，静态分析不等于动态执行。

不适用类别可合并说明原因，不为凑表填大量“通过”。通过后不重复运行相同检查；新修改、失败或新发现的影响范围才触发相关复测，最终证据必须对应最后一次相关修改后的代码。

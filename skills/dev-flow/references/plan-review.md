# 大需求计划评审

在可独立实施的大需求计划形成后、修改业务代码前使用。目标是在实现前发现需求和验收缺口，不把评审变成新的审批关卡，也不替代编码后的实际测试。

## 启动条件

计划已经成形，并满足以下任一项时自动双评审：

- 至少包含两个可分别验收的业务结果。
- 会改变关键业务状态或状态机、权限边界、不可逆数据迁移，或产生有业务后果的外部副作用（例如支付、通知、第三方写入）。
- 会改变跨模块接口或行为契约，并可能影响其他调用方。
- 存在多个可行业务路径或关键业务规则，当前仍有会影响用户结果的未决决策。

用户明确要求“产品与测试评审这个计划”或“评审计划”时，无论大小都执行一次。计划的目标、范围、业务流程、验收标准或核心实现策略发生实质变化时，对变化后的版本再评审。

满足任一判据即触发，即使计划表面只包含一个小型业务；只有未命中任何判据时，小型单业务计划、普通偏好项保存和其他低风险改动才按原有轻量流程处理。普通问答、非评审性质的方案讨论、纯进度更新和只改措辞不自动触发；单文件修改如果改变了上述关键状态或业务契约，仍按实际影响判断。批量重命名、格式化、依赖更新等没有行为变化的机械修改不触发。不为所有任务强制增加计划文档，也不要求用户先喊出“大需求”。

## 给两个角色同一份输入

两个子代理应拿到同一版计划，包括：

- 用户原始需求、已确认范围、明确不做的内容和不能改变的约束。
- 计划版本标识、目标、业务流程、关键决策、验收标准和预期交付物。
- 相关入口、数据与状态、外部依赖、已有测试和当前仓库状态；代码事实需标明已核实或仍待确认。
- 项目规则、已知环境限制和用户已经决定的取舍。

让两个角色独立阅读原始需求，不把主代理的结论当作既定事实，也不先传其中一方的评审结果。需要看代码时只做只读核对，不修改工作区、不推进已有改动。

## 两个独立角色

### 产品评审

从用户和业务结果判断计划是否合理：

- 问题与目标是否一致，范围和明确不做项是否完整。
- 主要角色、业务入口、流程节点和状态变化是否说得通。
- 业务规则、权限、数据口径、外部依赖和异常体验是否遗漏。
- 验收标准是否覆盖真实用户结果，是否存在未说明的假设或产品决策。
- 计划中是否有超出用户要求的功能，或会破坏现有业务约束的变化。

不应替代产品负责人新增功能，也不以技术偏好否决合理业务目标。

### 测试评审

从验收和风险判断计划是否可验证：

- 验收条件是否有可观察结果，能否转换为明确的输入、操作和预期输出。
- 正常路径、关键边界、失败与恢复、重复请求、权限和状态一致性是否覆盖。
- 受影响的调用方、数据迁移、兼容性和回归范围是否识别。
- 测试数据、隔离环境、依赖服务和执行入口是否可行；已有测试能否复用。
- 实施计划是否留下无法验证的空白，需要在编码前补齐哪些验收条件。

不要求为每个计划预先写完整测试用例，也不把实现方案当作预期行为。

## 独立委派

使用当前客户端可用的子代理能力启动两个角色，优先并行。两个角色使用独立代理实例，不能由一个代理扮演两种视角，也不让评审代理继续分派子代理。若只能顺序执行，先让两者各自形成结论再交给主代理，不能用前一角色的结论影响后一角色。

某角色无法启动、执行中断或输入不完整时，单次环境失败可重试一次；恢复后优先补跑缺失角色。仍然失败时记录该角色及未覆盖范围，主代理可做相称的只读补充检查，但最终必须标记为“仅产品完成／仅测试完成／双角色未完成”，不能说成双评审通过。

角色缺失本身不增加新的审批步骤。若缺失视角涉及关键范围、验收、权限、数据或回归，而且主代理无法用需求、代码或已执行检查核实，就把它保留为未解决阻碍，暂停相关实施；若缺口不构成材料风险，且已有实施授权，可以用现有依据继续，但在最终计划和交接中保留相同状态。存在会改变用户结果的关键产品决策缺口时，先澄清。两个角色同时不可用时，不用单角色或主代理自检冒充双评审。

## 汇总与修订

主代理把两份报告合并为问题清单，保留不同角色之间的分歧：

| 编号 | 视角 | 级别 | 计划位置与证据 | 影响 | 建议 | 处置 | 复验 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 按实际填写，如 F-001 | 产品／测试 | 阻碍／需澄清／建议 | 引用计划节点和事实依据 | 对范围、验收或风险的影响 | 可执行的最小修改 | 已解决／已推迟／已接受／待决定，附理由 | 需要复验时关联检查编号 |

需要长期追踪或交付时要机械核对时，把上表同步为 `dev-flow.findings.v1` 记录，字段定义见 [证据 Schema](evidence-schema.md#dev-flowfindingsv1)。阻碍项被推迟或标记已接受时，必须写明用户批准依据；要求复验的条目必须关联通过的检查，不能只写“已修复”。评审意见未闭环就进入编码或交付时，明确说明剩余项和风险。

只依据需求、代码事实和可验证的约束采纳意见。修订计划时保持用户已确认的范围；不得以“评审建议”为理由擅自增加功能、重写无关方案或开始编码。

关键业务取舍缺少事实依据、且不同选择会改变用户结果时，向用户提出具体问题。可以从需求、项目规则或现有行为确定的事项直接处理，不把每个建议都变成确认。

同一版本完成汇总和修订后，若目标、范围、业务流程、验收标准或核心实现策略发生实质变化，让两个角色分别复核新版和其关联风险。修订仅涉及措辞、序号或不改变行为的说明时不必重开评审。复审时某个角色失败，先重试该角色；仍然失败就保留新的缺失状态，并重新检查缺失视角是否构成材料阻碍。最终结论必须对应最后修订后的计划，不能沿用修订前“双角色完成”的状态。无新证据的重复争议应说明未解决项、风险和当前处理依据，不无限循环。

## 计划阶段的交付与接续

仅规划或 Plan 模式下，评审结束后的交付物是最终计划、主要评审意见和处理结果；不开始业务编码，也不自行切换模式。已有实施授权时，只有在没有未解决阻碍或关键产品决策缺口的情况下继续实施。

将评审确认的验收条件、关键场景和未解决风险交给编码后的独立测试阶段。计划评审通过只说明计划可以进入实施，不证明代码已正确实现；最终仍要测试真实代码并把测试证据写入交付说明。

跨会话交接时记录最终计划版本、产品与测试评审状态、已采纳事项、未解决项和下一步，不复制两份完整报告。

## 行为验收场景

在真实开发会话中按以下场景核对规则是否被执行；静态链接或格式检查不能代替行为验证。

| 场景 | 通过条件 |
| --- | --- |
| 计划未形成 | 不启动双评审，先补全计划和验收目标 |
| 命中“两个可分别验收的业务结果” | 两个独立角色收到同一版计划并先独立给出结论；计划评审不声称已测试代码 |
| 命中“关键业务状态或状态机变化” | 使用单文件实现也执行双评审 |
| 命中“权限边界变化” | 核对不同角色的允许与拒绝路径后执行双评审 |
| 命中“不可逆数据迁移” | 核对迁移、回滚和兼容边界后执行双评审 |
| 命中“有业务后果的外部副作用” | 支付、通知、第三方写入等场景执行双评审 |
| 小型业务同时改变权限或关键状态 | 敏感判据优先，仍执行双评审 |
| 命中“跨模块接口或行为契约变化” | 检查调用方影响和回归风险后再修订计划 |
| 命中“多个可行业务路径或关键未决规则” | 先区分需用户决定的问题和可由代码事实确认的问题 |
| 未命中任何判据的小型单业务计划、普通方案讨论、无行为变化的机械修改 | 不自动启动双评审，维持原有轻量流程；普通偏好项保存等低风险持久化不算命中 |
| 用户明确要求评审小计划 | 执行一次产品与测试双评审 |
| 计划实质修订或仅改措辞 | 前者由两个角色复核关联风险，后者不重开评审 |
| 仅规划或 Plan 模式 | 命中判据才双评审；评审后停在计划阶段，不编码、不自行切换模式 |
| 已有实施授权且无未解决阻碍 | 双评审或明确降级状态后继续实施 |
| 已有实施授权但缺失视角涉及材料风险 | 主代理无法核实时暂停相关实施，保留未解决阻碍 |
| 单角色失败 | 重试一次后补跑或标记“仅产品完成／仅测试完成”；关键缺口未被核实时不冒充通过或继续推进 |
| 双角色失败 | 标记“双角色未完成”，不用主代理自检代替双评审 |
| 修订后角色结果 | 最终状态对应最新版计划，分别验证双角色完成、仅产品完成、仅测试完成、双角色未完成，不沿用旧版结论 |
| 编码完成 | 计划测试视角不计作动态测试；实际运行最终代码并在修改后复测相关场景 |
